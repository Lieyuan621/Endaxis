# 文档维护

文档帮助读者使用项目、理解设计和完成修改。内容按主题和读者任务组织，不按开发日期、对话顺序或某次重构组织。

## 文档放在哪里

| 位置                     | 回答的问题                                   |
| ------------------------ | -------------------------------------------- |
| 根 `README.md`           | 项目是什么，怎样开始，去哪里继续阅读         |
| `CONTRIBUTING.md`        | 怎样提出并验证一项修改                       |
| `docs/guide.md`          | 用户怎样操作，结果表示什么                   |
| `docs/architecture/`     | 模块为什么这样划分，数据如何流动，边界是什么 |
| `docs/development/`      | 怎样配置环境、检查代码和开发界面             |
| `tools/<工具>/README.md` | 工具的输入、命令、输出与失败处理             |
| 类型和函数注释           | 字段含义、单位、参数和局部不变量             |

组件与内部数据模块的共性说明归对应主题页，不默认每个目录都写 README。只有能独立使用、确实需要独立说明的模块才增加入口。工具命令只在所属工具说明维护。

## 描述最终设计

架构页说明稳定的职责、数据流与约束，不罗列迁移批次、替换数量或临时兼容入口。使用页说明产品行为，不把开发计划写成已经可用的功能。

设计尚未落实的缺口、临时工作区安排和待验收内容留在任务记录。正式接受的新设计需要更新对应主题，并让实现和验证跟上；不在公共文档中同时保留几套互相冲突的方案。

不使用团队内部的版本代号，不提读者无法访问的私有仓库，不依赖本机目录或私有研究才能理解说明。需要公开依据时引用可访问、能支持该结论的来源；不能公开的材料不伪装成公共链接。

## 怎样写

开头先说明这页解决什么问题。操作文档按前提、步骤、结果、失败处理排列；架构文档按职责、数据流、关键选择及代码入口排列。

先用普通语言解释，再给代码标识符。例如写“保存切面会记录当前战斗状态；尚未提交的技能安排由调用方保存”，不要只写“持久边界与未来后缀隔离”。

每个概念维护一处完整说明，其他页面链接过去。避免复制接口清单、阶段汇报、测试数量和“本轮已接入”等过程性表述。已完成计划直接移出公共文档，历史由 Git 保存。

## 哪些内容不提交

个人环境、服务状态、转储、原始解包文件、私有存档、账户信息、一次性审计和任务交接不提交到仓库。存放位置由开发者自行决定。

必要的小型测试夹具、生成定义和可复现研究结论可以提交，但要有明确消费者和来源；不能简单按“生成文件”或“带日期”决定保留与否。公开研究必须交代输入、方法、版本与限制，而不是只贴本机结果。

## 修改后检查

检查相对链接、章节锚点和代码路径；移动页面后搜索旧引用。检查命令是否对应真实入口，示例是否泄露个人信息。使用格式检查与 `git diff --check`，不为纯文档修改运行整套战斗测试。
